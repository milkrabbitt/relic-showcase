# 工程案例

## 重试与免费次数结算

**问题。** 移动网络中超时不代表请求未完成；再次提交可能重复生成、重复扣减。多气泡又会使“几条消息算一次”模糊。

**实际方案。** 以逻辑请求为单位保存幂等结果；成功提交一组回复时只结算一次，失败不写假回复、不扣次数。客户端对结果未知的请求先查询已有结果，保留原请求标识。记忆更新失败与已提交回复分别处理。

**权衡。** 用户可能先看到处理中，不能用一个新请求掩盖不确定结果。模型调用预算与用户试聊额度分别限制。

**验证。** 本地隔离用例覆盖失败、同请求重试及并发；隔离真实模型完成过一次多气泡逻辑回复和已完成态并发回执恢复，未重复结算。不是生产负载测试，也不代表所有云端在途故障注入已完成。

## 导入与人物确认

**问题。** 文件格式、说话人和文本长度不确定；未经核对直接生成画像会误用素材。

**实际方案。** 文件或电脑配对上传进入草稿，预览与说话人确认后才进入画像流程；客户端提前显示长度条件，服务端仍权威校验。失败保留已有有效人物卡。

**权衡。** 增加确认步骤，但用户能控制所用素材。电脑授权上传和机器人授权分开。

**验证。** 本地有异常/重复/权限及失败保留测试，后端和微信中转有隔离验证。完整手机光学扫码上传仍待验；不宣称兼容未经验证的全部聊天导出工具版本。

## 双端身份与共享

**问题。** “账号已绑定”容易被误说成“全部历史数据已同步”。

**实际方案。** Apple与微信分别经可信验证，绑定有时效、防重放与冲突规则；只共享明确的新角色，旧数据与余额不自动合并。资料和人工记忆更新检查修订；删除保留拒绝旧任务复活的状态。

**权衡。** 旧角色暂留原归属，用户不会因绑定意外丢失或叠加额度。

**验证。** 既有真实绑定保留；iPhone编辑隔离资料后真实微信中转读到，反向更新在iPhone可见。手机小程序完整共享、手工记忆双向编辑及双端删除UI传播仍待验。
